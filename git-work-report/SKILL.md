# Git 工作周报

## 概览

按明确日期范围收集当前工作区内多个 Git 仓库的提交，并整理成适合周报、日报、例会同步的中文业务汇报。先调用 `scripts/collect_git_commits.py` 采集结构化数据，再做去噪、聚合和业务翻译。

## 工作流

### 1. 解析时间

- 将自然语言时间解析为 `Asia/Shanghai` 下的绝对日期。
- 在内部锁定 `since` 和 `until` 的 `YYYY-MM-DD` 值，再调用脚本。
- 用户给出相对时间时，先换算为绝对日期；如果语义存在轻微歧义，采用最常见的业务解释，并在最终输出中使用绝对日期。

### 2. 采集提交

- 优先扫描用户当前工作区根目录下 3 层内的 Git 子仓库。
- 调用 Skill 自带脚本：

```bash
python3 <skill-dir>/scripts/collect_git_commits.py \
  --root <workspace-root> \
  --since <YYYY-MM-DD> \
  --until <YYYY-MM-DD>
```

- 用户只想汇总部分仓库时，重复传入 `--repo <path>`。
- 用户需要覆盖默认作者集合时，重复传入 `--author <pattern>`。
- 默认作者集合为：
  - `heqidong`
  - `何啟东`
  - `soft_nts.localheqidong`
  - `heqidong@cet-electric.com`

### 3. 做去噪

- 直接依赖脚本的 `--no-merges` 行为排除 merge commit。
- 继续忽略缺乏汇报价值的提交，例如：
  - 仅版本号、镜像名、锁文件或临时构建参数微调，且无法形成可汇报结果。
  - 仅 `fix`、`update`、`test`、`refactor` 等无上下文短句。
  - 仅临时试验、占位资源、空提交说明或无法判断目标的噪音提交。
- 证据不足时不要臆测业务目标，宁可保守表述为“完善打包配置”“修复会话状态问题”。

### 4. 做业务翻译与聚合

- 按“模块 / 目标 / 用户可感知结果”合并相近提交，不逐条复述 commit。
- 将代码语言翻译为业务语言，同时保留必要技术名词，避免空泛套话。
- 默认归类到以下三类：
  - `需求开发`
  - `缺陷修复`
  - `架构/工程优化`
- 空分类不要输出。
- 不得编造成果，不得把准备性工作夸大成上线结果。

### 5. 输出周报

- 仅输出 Markdown 中文正文，不附原始 commit 附录。
- 先写明统计周期，再按分类输出聚合后的工作结果。
- 如果整个时间段内没有匹配提交，直接输出：`该时间段内未发现匹配提交。`

## 输出模板

默认输出结构参考以下形式：

```md
统计周期：2026-03-09 至 2026-03-11

### 需求开发
- 完成……

### 缺陷修复
- 修复……

### 架构/工程优化
- 优化……
```

## 脚本说明

`scripts/collect_git_commits.py` 只负责确定性采集和结构化输出，不负责业务翻译。

- 必填参数：
  - `--root`
  - `--since`
  - `--until`
- 可选参数：
  - `--repo`
  - `--author`
- 输出 JSON，包含：
  - `stats`
  - `commits`
- `commits` 中每条记录包含：
  - `repo_name`
  - `repo_path`
  - `hash`
  - `author_name`
  - `author_email`
  - `date`
  - `subject`
  - `body`

## 约束

- 保持中文输出，确保内容可直接粘贴到周报或例会文档。
- 合并同主题碎片提交后再落笔，不要把同一件事拆成多条废话。
- 遇到跨前后端、跨多个仓库但目标一致的提交时，允许合并成一条业务结果。
- 发现脚本返回空结果时，直接如实说明，不要构造补充内容。
